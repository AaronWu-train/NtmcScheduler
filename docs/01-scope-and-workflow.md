# 01. 第一版範圍與營運流程

## 1. 文件目的

讓未參與需求討論的開發者（或 AI agent）只依本組文件即可理解名詞、規則、跨月邊界與系統責任，
並實作出可驗收的系統。若實作時遇到文件未定義的業務情況，**應回報規格缺口，不得自行補上業務假設**。

## 2. 第一版範圍

| 納入第一版 | 不納入第一版 |
|---|---|
| 站務 M、檢測 T 的月排班 | 行控 S |
| R、R\*、R1、R休、X、跨月歷史、延伸排班日 | 自動建立或調整萬年班表模板 |
| M 八週萬年班表僅作 CP-SAT solution hint | 行控／T 萬年班表 |
| 最多 3 份候選、同月多版本、人工修改、唯一 `★` 採用版 | 自動提供人工調整建議 |
| CSV 匯入匯出、Blazor 操作、登入授權、稽核紀錄 | 月中調站、月中到職／離職 |
| 本組文件列出的工時與休假規則 | 其他週／月工時、加班上限、夜班次數限制 |
| 有效 M／T 人員 | PA、簽名欄、顏色及班表以外內容 |

補充邊界：

- **PA**：不讀取、不排班、不統計。
- 第一版視所有人員資料**整個月有效**（無月中異動）。
- 第一版使用本機帳號登入。所有已登入者可檢視 M/T；Administrator 管理帳號，M/T 編輯權分開授予。S 尚無業務規格，不建立空殼介面。

## 3. 班表生命週期

```
Demand 工作檔可持續修改或刪除 → 輸入驗證 → 求解（最多 3 份候選）→ 保存為獨立班表版本 → 人工修改（自動存檔＋驗證）→ 標示採用版本 ★。每次求解保存當下輸入快照；後續修改、重建或刪除 Demand 不影響既有求解紀錄與班表。
```

1. **驗證**：系統驗證人員、班組、歷史、R\*／X 與固定設定；任何錯誤回傳
   `INVALID_INPUT`（完整清單見 `03-data-and-validation.md`）。
2. **求解**：建立 M 或 T 模型，依固定 Priority 群組做字典序最佳化，嘗試產生最多 3 份嚴格候選
   （見 `06-solver-and-output.md`）。
3. **保存版本**：每份候選保存為獨立、可編輯的班表版本；同單位同月份可有多份版本。
4. **人工修改**：任何未封存版本都可在互動寬表逐格修改；每次修改自動保存，由後端驗證服務
   重新檢查規則與 Coverage。允許暫存違規狀態，但必須立即標示。
5. **採用與封存**：同單位同月份最多一份班表標示為 `★`。有 P0 或 Coverage 違反時不可標示；
   已採用版本必須先改選其他版本才能封存。封存只隱藏，不實體刪除資料或稽核紀錄。

## 4. 版本與歷史規則

- 同一單位、同一月份可保存多份 `ScheduleVersion`，`AdoptedSchedule` 最多指向其中一份作為 `★` 採用版。
- 求解器 PreviousMonth 優先取上月 `★`；沒有時必須上傳完整、已解析的 previous schedule。
- 在建立班表的「上月班表」步驟上傳 previous schedule 時，同一份內容也保存為上月的 Imported 歷史班表版本；規則或人力問題只標記警告，不阻擋採用。使用者可開啟、自由編輯、採用並作為本月求解的歷史來源。
- `★` 班表與 X 事件是後續排班的正式歷史來源，求解器不得改寫（規則 GEN-H-05）。
- 每次 ScheduleRun 保存完整快照：人員、事件、歷史截止點、固定設定、
  隨機種子（seed）與程式版本，重跑可重現。
- 八週區間、國定假日與非常態班型每次修改建立不可變設定版本；既有 Demand、Run 與班表不回溯套用新設定。

## 5. 規模與效能目標

| 項目 | 第一版要求 |
|---|---|
| 規模 | M 最多約 48 人／12 站；T 最多約 30 人（每班組約 10 人） |
| 求解時限 | 單次總求解目標 **5 分鐘內**；逾時且有合法解則回傳並標示 `TIME_LIMIT` |
| 背景工作 | ScheduleRun 先寫入資料庫，再由 BackgroundService 一次執行一個 Solver |
| 重啟 | Queued／Running 的工作可依快照重新開始（不宣稱續跑原搜尋狀態） |
