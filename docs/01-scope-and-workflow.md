# 01. 第一版範圍與營運流程

## 1. 文件目的

讓未參與需求討論的開發者（或 AI agent）只依本組文件即可理解名詞、規則、跨月邊界與系統責任，
並實作出可驗收的系統。若實作時遇到文件未定義的業務情況，**應回報規格缺口，不得自行補上業務假設**。

## 2. 第一版範圍

| 納入第一版 | 不納入第一版 |
|---|---|
| 站務 M、檢測 T 的月排班 | 行控 S |
| R、R\*、R1、R休、X、跨月歷史、延伸排班日 | 萬年班表 |
| 最多 3 份候選、目前班表人工修改、可選快照 | 自動提供人工調整建議 |
| CSV 匯入匯出、Blazor 操作、稽核紀錄 | 月中調站、月中到職／離職 |
| 本組文件列出的工時與休假規則 | 其他週／月工時、加班上限、夜班次數限制 |
| 有效 M／T 人員 | PA、簽名欄、顏色及班表以外內容 |

補充邊界：

- **PA**：不讀取、不排班、不統計。
- 第一版視所有人員資料**整個月有效**（無月中異動）。
- 第一版**不做登入與角色權限**；所有功能對開啟系統者開放（決策 D-04，擴充點見 `07-architecture.md`）。

## 3. 班表生命週期

```
輸入驗證 → 求解（最多 3 份嚴格候選）→ 選一份成為目前班表 → 人工修改（自動存檔＋驗證）
```

1. **驗證**：系統驗證人員、班組、歷史、R\*／X 與固定設定；任何錯誤回傳
   `INVALID_INPUT`（完整清單見 `03-data-and-validation.md`）。
2. **求解**：建立 M 或 T 模型，依優先順序逐條最佳化，嘗試產生最多 3 份嚴格候選
   （見 `06-solver-and-output.md`）。
3. **選目前班表**：使用者選一份候選，立即成為該單位該月份的「目前班表」並保存；
   若已有目前班表須先確認是否取代。Candidate 本身不可直接修改。
4. **人工修改**：目前班表可在互動寬表逐格修改；每次修改自動保存，後端以
   `RuleEvaluationEngine` 重新檢查規則與 Coverage。允許暫存違規狀態，但必須立即標示。
5. **快照（可選）**：可手動建立唯讀快照或從歷史匯入載入；無審核／發布狀態機。

## 4. 版本與歷史規則

- 同一單位、同一月份，任何時刻**只有一份**「目前班表」（`MonthSchedule`）。
- 歷史匯入與手動快照寫入 `ScheduleSnapshot`；求解器 Histories 優先取目前班表，
  其次取該月 `IsCurrent` 快照（見決策 D-20）。
- 目前班表與 X 事件是後續排班的正式歷史來源，求解器不得改寫（規則 GEN-H-05）。
- 每次 ScheduleRun 保存完整快照：人員、事件、歷史截止點、固定設定、規則順序、
  隨機種子（seed）與程式版本，重跑可重現。

## 5. 規模與效能目標

| 項目 | 第一版要求 |
|---|---|
| 規模 | M 最多約 48 人／12 站；T 最多約 30 人（每班組約 10 人） |
| 求解時限 | 單次總求解目標 **5 分鐘內**；逾時且有合法解則回傳並標示 `TIME_LIMIT` |
| 背景工作 | ScheduleRun 先寫入資料庫，再由 BackgroundService 一次執行一個 Solver |
| 重啟 | Queued／Running 的工作可依快照重新開始（不宣稱續跑原搜尋狀態） |
